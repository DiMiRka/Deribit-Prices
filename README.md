# Deribit Prices

Сервис раз в минуту забирает с криптобиржи [Deribit](https://docs.deribit.com/) индексные цены, сохраняет их в PostgreSQL (тикер, цена, время в UNIX timestamp) и отдаёт сохранённые данные через HTTP API на FastAPI

**Стек:** Python 3.12, FastAPI, aiohttp, SQLAlchemy 2 (async) + asyncpg, Alembic, Celery + Redis, PostgreSQL 17, pydantic-settings, loguru, pytest, ruff, mypy (strict), Docker Compose

## Архитектура

```text
┌────────┐ задача раз ┌───────┐  забирает  ┌────────┐  HTTP GET  ┌─────────┐
│  beat  │ ─────────► │ Redis │ ─────────► │ worker │ ─────────► │ Deribit │
└────────┘  в минуту  └───────┘   задачу   └───┬────┘            └─────────┘
                                               │ INSERT
                                               ▼
┌────────┐  GET /prices…  ┌───────────┐       ┌────────────┐
│ клиент │ ─────────────► │    app    │ ────► │ PostgreSQL │
└────────┘                │ (FastAPI) │       └────────────┘
                          └───────────┘
```



```text
app/
├── api/            # HTTP слой: роутер /prices, зависимости (валидация параметров, сборка сервиса)
├── clients/
│   └── deribit/    # клиент Deribit на aiohttp (запрос, разбор ответа, свои исключения)
├── core/           # настройки (pydantic-settings) и логирование (loguru)
├── db/             # модель Price, базовый класс, класс Database (engine + фабрика сессий)
├── repositories/   # PriceRepository (все SQL-запросы)
├── schemas/        # enum Ticker (список индексов), pydantic схема ответа API, параметры запроса
├── services/       # PriceService (чтение), PriceCollector (сбор с биржи и сохранение)
├── worker/         # фабрика Celery, задача collect_prices, точка входа для CLI
└── main.py         # фабрика FastAPI приложения
alembic/            # миграции БД
tests/              # unit тесты (без внешних сервисов)
```

Путь одного сбора: `beat` по расписанию кладёт задачу `collect_prices` в Redis → `worker` выполняет её → `PriceCollector` параллельно запрашивает цены по всем тикерам через `DeribitClient` → успешные результаты сохраняются через `PriceRepository` одной транзакцией

## Запуск в Docker

```bash
git clone <repo-url> deribit-prices
cd deribit-prices
cp .env.example .env
docker compose up --build -d
```

Поднимется шесть сервисов:

| Сервис | Назначение |
|---|---|
| `db` | PostgreSQL 17, данные в volume `pgdata` |
| `redis` | брокер сообщений для Celery |
| `migrate` | одноразово применяет миграции (`alembic upgrade head`) и завершается |
| `app` | FastAPI на http://localhost:8000 |
| `worker` | Celery worker, выполняет сбор цен |
| `beat` | Celery beat, раз в минуту ставит задачу сбора в очередь |

Порядок старта контролируется через `depends_on` + healthcheck (`db` готова → `migrate` успешно завершился → стартуют `app` и `worker`)

## Локальный запуск

Нужны Python 3.12+ и локально запущенные **PostgreSQL** (14+) и **Redis** (адреса сервисов берутся из `.env`)

1. Создать пользователя и базу данных PostgreSQL (значения должны совпадать с `POSTGRES_*` в `.env`)

   ```sql
   CREATE USER admin WITH PASSWORD 'admin';
   CREATE DATABASE deribit OWNER admin;
   ```

2. Создать и активировать виртуальное окружение

   ```bash
   python -m venv .venv
   source .venv/bin/activate        # Windows: .venv\Scripts\activate
   ```

3. Установить зависимости (вместе с инструментами для тестов и линтеров)

   ```bash
   pip install -r requirements-dev.txt
   ```

4. Создать `.env` (в `.env.example` уже прописаны адреса `localhost`)

   ```bash
   cp .env.example .env
   ```

5. Применить миграции

   ```bash
   alembic upgrade head
   ```

6. Запустить три процесса, каждый в своём терминале

   ```bash
   uvicorn app.main:create_app --factory --reload   # API на http://localhost:8000
   celery -A app.worker.main worker                 # выполняет сбор цен
   celery -A app.worker.main beat                   # раз в минуту ставит задачу в очередь
   ```

   > Стандартный пул процессов Celery (prefork) на Windows не работает, воркер запускается с `--pool=solo`
   > (`celery -A app.worker.main worker --pool=solo`)

## API

У трёх методов из ТЗ (`/prices/history`, `/prices/latest`, `/prices/by-date`) обязателен query параметр `ticker` (регистр не важен)\
Дополнительный метод `/prices` возвращает последние цены сразу по всем тикерам

### `GET /prices` последние цены по всем тикерам

Дополнительный метод сверх обязательных по ТЗ, поэтому параметра `ticker` у него нет (возвращает последнюю цену по каждому тикеру в порядке объявления в `Ticker`)

```bash
curl "http://localhost:8000/prices"
```

```json
[
  {"ticker": "btc_usd", "price": "81213.58000000", "timestamp": 1792058071, "datetime": "2026-10-15T09:54:31Z"},
  {"ticker": "eth_usd", "price": "2373.71000000", "timestamp": 1792058071, "datetime": "2026-10-15T09:54:31Z"}
]
```

### `GET /prices/history` все сохранённые цены по тикеру

| Параметр | Тип | По умолчанию | Описание |
|---|---|---|---|
| `ticker` | string | — | обязательный |
| `limit` | int | `100` | от 1 до 1000 |
| `offset` | int | `0` | ≥ 0 |

Записи отсортированы по времени по возрастанию

```bash
curl "http://localhost:8000/prices/history?ticker=btc_usd&limit=2"
```

```json
[
  {"ticker": "btc_usd", "price": "81213.58000000", "timestamp": 1792058071, "datetime": "2026-10-15T09:54:31Z"},
  {"ticker": "btc_usd", "price": "81200.47000000", "timestamp": 1792058131, "datetime": "2026-10-15T09:55:31Z"}
]
```

### `GET /prices/latest` последняя цена по тикеру

```bash
curl "http://localhost:8000/prices/latest?ticker=eth_usd"
```

```json
{"ticker": "eth_usd", "price": "2372.76000000", "timestamp": 1792058131, "datetime": "2026-10-15T09:55:31Z"}
```

### `GET /prices/by-date` цены по тикеру с фильтром по дате

| Параметр | Тип | По умолчанию | Описание |
|---|---|---|---|
| `ticker` | string | — | обязательный |
| `date_from` | дата или дата и время | — | нижняя граница, включительно, необязательный |
| `date_to` | дата или дата и время | — | верхняя граница, включительно, необязательный |
| `limit`, `offset` | int | `100`, `0` | как у `/prices/history` |

```bash
curl -G "http://localhost:8000/prices/by-date" \
  --data-urlencode "ticker=btc_usd" \
  --data-urlencode "date_from=2026-10-15 09:50" \
  --data-urlencode "date_to=2026-10-15 09:55"
```

```json
[
  {"ticker": "btc_usd", "price": "81213.58000000", "timestamp": 1792058071, "datetime": "2026-10-15T09:54:31Z"}
]
```

Форматы границ (время в UTC):

| Значение | Как понимается                       |
|---|--------------------------------------|
| `2026-10-15` | дата (15.10.2026 с `00:00:00`)       |
| `2026-10-15 12:30` | дата и время (15.10.2026 `12:30:00`) |

Для совместимости принимаются и технические форматы UNIX timestamp (`1792058071`) и ISO 8601 с часовым поясом (`2026-10-15T09:54:31Z`, `2026-10-15T12:54:31+03:00`)

Каждая запись в ответах содержит `timestamp` (UNIX секунды как хранится в БД) и `datetime` (то же время, но в удобном для человека формате)

## Design decisions (проектные решения)

### Цена: `Decimal` в Python и `NUMERIC(20, 8)` в БД

`float` хранит числа в двоичном виде и не может точно представить большинство десятичных дробей (`0.1 + 0.2 == 0.30000000000000004`)\
Для цен такие ошибки недопустимы, поэтому цена на всём пути остаётся точной:

- ответ Deribit разбирается pydantic сразу в `Decimal` **из текста JSON** (без промежуточного `float`)
- в БД `NUMERIC(20, 8)`: 8 знаков после запятой (стандарт для криптовалют, 1 сатоши = 10⁻⁸ BTC) и 12 знаков до запятой с запасом
- в JSON ответе API цена отдаётся **строкой** (`"81213.58000000"`), JSON число многие клиенты (например, JavaScript) прочитают как `float` и потеряют точность

### Время записи: время сервера Deribit (`usOut`)

В таблицу пишется `usOut` из ответа Deribit (время формирования ответа на стороне биржи, в микросекундах), переведённое в UNIX секунды\
Это момент когда биржа отдала цену (он не зависит от сетевой задержки, очереди Celery и точности часов нашего сервера)

### Индекс `(ticker, timestamp)`

Составной B-tree индекс обслуживает все текущие запросы API:

- все цены по тикеру (`WHERE ticker = ?`) использует левую часть индекса
- последняя цена (`ORDER BY timestamp DESC LIMIT 1`) читается с конца участка тикера (`Index Scan Backward`) без сортировки
- фильтр по дате (диапазон `timestamp` внутри участка тикера)
- последние цены по всем тикерам (тот же `Index Scan Backward` + `LIMIT 1`, выполненный для каждого тикера внутри `JOIN LATERAL`)

### Параллельный сбор и изоляция ошибок

`PriceCollector` запрашивает все тикеры одновременно через `asyncio.gather(..., return_exceptions=True)`, время сбора данных равно времени самого медленного запроса, а не сумме\
Флаг `return_exceptions=True` нужен чтобы ошибка по одному тикеру не потеряла остальные (без него `gather` выбросит первое исключение, и успешные результаты пропадут)

- `DeribitError` (сеть, таймаут, ошибка API) ожидаемая ситуация (пишем предупреждение в лог, сохраняем остальные цены)
- любое другое исключение это ошибка в коде, она пробрасывается дальше, чтобы не быть тихо проглоченной


### Клиент Deribit

- Ошибка проверяется по полю `error` JSON RPC, а не только по HTTP-статусу (на неверный индекс Deribit отвечает `400` и объясняет причину в `error`)
- Своя иерархия исключений (`DeribitNetworkError`, `DeribitResponseError`, `DeribitAPIError` от общего `DeribitError`), остальной код не зависит от aiohttp и различает причины сбоя
- `aiohttp.ClientSession` передаётся в клиент снаружи (одна сессия и пул соединений на запуск сбора, временем её жизни управляет вызывающий код)
- Повторных попыток внутри клиента нет (следующий сбор через минуту, а повтор с задержкой мог бы наложиться на него)

### Celery

Соединения asyncpg привязаны к loop в котором созданы, поэтому engine БД создаётся и закрывается на каждый запуск, а не один на процесс (раз в минуту это ничего не стоит, зато нет ошибки `attached to a different loop`)


Брокер **Redis**, для одной периодической задачи он проще RabbitMQ в настройке и эксплуатации, а гарантий доставки уровня RabbitMQ задаче которая повторяется каждую минуту не нужно

### Расписание: crontab, а не интервал

Сбор запускается по cron-выражению `* * * * *` в начале каждой календарной минуты (UTC)

Изначально было интервальное расписание (каждые 60 секунд), но при проверке сон процесса растягивался, и запуски шли раз в ~66 секунд. Интервал копит такое отставание (за час ~55 сборов вместо 60), а crontab каждый раз сверяется с часами (опоздание одного запуска не переносится на следующие, в каждой минуте ровно один сбор)

Дополнительно у задачи `expires = 60` секунд, если worker был недоступен накопившиеся в очереди устаревшие задачи отбрасываются, а не выполняются пачкой


### Без глобальных переменных

- Настройки: `get_settings()` с `@lru_cache` (объект создаётся при первом обращении, а не при импорте), в FastAPI он приходит через `Depends(get_settings)` и может быть подменён через `dependency_overrides`, а в Celery и тестах `Settings` передаётся явно
- FastAPI: фабрика `create_app()` (`uvicorn ... --factory`), движок БД создаётся в `lifespan`, хранится в `app.state` и закрывается при остановке
- Сессия БД, репозиторий и сервис собираются на каждый запрос через цепочку `Depends`
- Celery: фабрика `create_celery_app(settings)`, задача объявлена через `@shared_task` (не привязана к глобальному объекту приложения)
- Единственный объект уровня модуля в `app/worker/main.py`, CLI Celery умеет работать только с готовым объектом, а не с фабрикой (этот модуль точка входа и никем не импортируется)
- Константы (`MAX_LIMIT`, формат логов) и `APIRouter` это неизменяемые объявления, а не состояние

### API

- **Тикер `StrEnum Ticker` единственный источник правды** для сборщика и API\
  FastAPI сам проверяет значение (неизвестное → `422` со списком допустимых), а в OpenAPI попадает `enum`, поэтому Swagger показывает выпадающий список.\
  `StrEnum` является одновременно строкой, так что значение напрямую идёт в SQL и запрос к Deribit
- **Пагинация `limit/offset`** с верхней границей 1000\
  Таблица растёт на ~2880 строк в сутки, отдавать всё одним ответом нельзя.\
  Сортировка **по возрастанию** времени (новые записи добавляются в конец, и уже выданные страницы не сдвигаются)
- **`/prices` (последние цены по всем тикерам) - один SQL-запрос с `JOIN LATERAL`**\
  Список тикеров разворачивается в таблицу через `unnest ... WITH ORDINALITY`, и для каждого выполняется подзапрос `ORDER BY timestamp DESC LIMIT 1` по индексу.\
  Альтернативы хуже: `get_latest` в цикле это N запросов к БД (распараллелить через `gather` нельзя, одна `AsyncSession` не поддерживает параллельные запросы), а `DISTINCT ON (ticker)` читает все строки этих тикеров, чтобы выбрать по одной.\
  Порядок ответа совпадает с порядком в `Ticker` (сортировка по номеру тикера в списке).\
  Тикеры без данных не попадают в ответ (так все методы возвращают одну схему `PriceRead` с обязательными полями, а не ослабленную схему с `null`)
- **Даты в API UNIX и ISO 8601.** \
  В БД время хранится в UNIX секундах, как требует ТЗ, но человеку удобнее ISO 8601.\
  Поэтому параметры фильтра объявлены как `datetime` (FastAPI принимает привычные `2026-10-15` и `2026-10-15 12:30`, а также UNIX секунды и ISO 8601 с часовым поясом).\
  Время без пояса считается UTC (иначе результат зависел бы от часового пояса сервера).\
  В зависимости границы переводятся в UNIX-секунды (нижняя округляется вверх, верхняя вниз, чтобы дробные секунды не расширяли диапазон), поэтому сервис, репозиторий и SQL работают только с целыми числами.\
  В ответе к `timestamp` добавлено вычисляемое поле `datetime` (ISO 8601 UTC, `@computed_field`), при этом в БД ничего не добавляется

### Контейнеры Docker: шесть вместо двух

ТЗ упоминает приложение и БД, но Celery требует брокер и два отдельных процесса\
Принцип «один контейнер - один процесс» (Docker следит за каждым процессом и перезапускает упавший, логи не смешиваются, worker можно масштабировать независимо, а beat держать в одном экземпляре)

- Один образ для `app`, `worker`, `beat` и `migrate` (различается только команда)
- **Миграции в отдельном одноразовом сервисе `migrate`**, применяются до старта и API, и worker (иначе worker мог бы стартовать раньше таблицы), не гонятся параллельно при нескольких экземплярах `app`, а при ошибке миграции зависимые сервисы не запускаются
- Образ: `python:3.12-slim`, только рабочие зависимости (без pytest/mypy), запуск от непривилегированного пользователя, слой зависимостей кешируется отдельно от кода
- PostgreSQL и Redis опубликованы только на `127.0.0.1`: к ним можно подключиться с хоста (например, клиентом БД), но не снаружи машины

### Логирование: loguru

Короткая настройка и читаемый формат\
Записи стандартного `logging` (uvicorn, Celery, SQLAlchemy, Alembic) перехватываются и выводятся в том же формате\
Celery по умолчанию перенастраивает логирование при старте (это отключено подпиской на сигнал `setup_logging`)
